# Deep 研究协议

Deep 模式用于回答“他们到底怎么做的、为什么、能否借鉴、应该放在哪层”这类会影响设计判断的问题。目标不是读取尽可能多的文件，而是让关键结论可复查。

## 1. 把宽泛请求改写成研究问题

先列出 1–3 个会改变最终判断的问题，例如：

- 这个能力的真实运行入口和生命周期是什么？
- 核心扩展边界由哪个抽象拥有？
- 配置变化如何传到运行时状态？
- 故障、取消、回滚和资源清理怎么处理？
- 来源机制依赖哪些语言或运行时特性，目标系统是否具备？

问题决定读取范围。若一条证据链已经足够回答窄问题，就停止；不要机械满足文件数或调用链配额。

## 2. 固定研究基线

研究源码前解析默认分支、tag 或用户指定 ref 的 commit SHA，并在报告中记录：

```yaml
source_ref: main
resolved_sha: <40-char SHA>
accessed_at: <ISO timestamp>
```

决策性源码链接使用固定 SHA。Issue、PR、release、规范和官方文档使用稳定 URL，并记录访问日期。用户明确询问“当前最新”时仍以当前状态为目标，只是在研究开始时记录所解析的 revision。

## 3. 按问题选择证据

| 问题 | 优先证据 |
|---|---|
| 当前行为 | 入口源码、核心实现、测试、失败路径 |
| 对外契约 | 规范、官方文档、公开类型/API、契约测试 |
| 设计动机 | ADR、设计文档、PR discussion、review、关键 commit |
| 已知故障 | Issue 正文与评论、关闭原因、修复 PR、受影响版本 |
| 版本演进 | tag、release note、compare、关键文件 diff、迁移文档 |
| 论文或理念 | 论文正文、作者材料、对应实现及其测试 |

README 用于建立术语和入口，不单独证明内部架构。

## 4. 形成闭合证据链

一条闭合链通常包含：

```text
用户可见入口
  → 配置/构造
  → 核心抽象
  → 运行时状态变化
  → 输出、失败或清理
  → 覆盖该行为的测试/历史证据（问题需要时）
```

动态注册、反射、宏、生成代码、事件总线或 FFI 可能无法静态确认完整调用图。此时明确写“已确认边”和“推测边”，不要伪造确定性。

## 5. 跨项目借鉴

GitHub KB 只建立来源侧事实。主 Agent 另外检查目标项目，并用下表合成：

| 来源机制 | 解决的问题 | 依赖的前提 | 目标位置 | 冲突/缺口 | 判断 |
|---|---|---|---|---|---|

未取得目标架构证据时，输出条件式方案和需要补查的目标位置，不给确定落点。

## 6. 续问与收束

续问不是重新启动整仓研究。先复述当前有效的研究基线和已确认结论，再把新问题改写成一个增量问题：它会改变哪项判断，还缺哪条证据？

- 来源仓库和 ref 未变时，复用已有 resolved SHA、术语、入口和证据链。
- 只打开增量问题需要的源码、测试、PR 或文档，不重新生成蓝图或重复搜索相同候选。
- 用户改问“当前最新”、切换 ref、上次采集不完整，或新事实可能推翻基线时，才刷新 revision 并说明原因。
- “借鉴什么”先给最小可迁移单元和不该吸收项；来源项目复杂，不代表目标项目也要复制同等层级、组件或流程。
- 用户没有要求修改目标项目时，停在建议和证据，不把研究自动扩张成设计或实现任务。

当 1–3 个研究问题已有足够证据、剩余不确定性不会改变当前行动建议时结束 Deep。停止是研究质量的一部分：更多文件和更多链接不自动产生更可靠的判断。

## 7. 报告结构

```markdown
# 研究问题
## 结论
## 研究基线
## 机制与证据链
## 为什么这样设计
## 边界、反例与未确认项
## 对目标系统的启示（仅在目标已检查时）
## 关键证据
```

关键结论附近放来源链接。最后列出最重要的固定 revision 源码、测试、PR/Issue 或规范，不用堆砌与判断无关的链接。
