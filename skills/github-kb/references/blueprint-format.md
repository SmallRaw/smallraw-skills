# 蓝图格式参考

蓝图是对一个 GitHub 仓库的结构化总结。脚本负责采集原始数据，你负责在此基础上做智能分析。

## 蓝图结构

蓝图的核心逻辑是：**先讲清楚这个项目是什么、为什么值得关注，再深入架构细节**。读者需要先建立兴趣和背景认知，才有动力去挖掘设计细节。

```markdown
---
repo: owner/repo
generated: YYYY-MM-DD
type: blueprint
---

# <Repo Name> 蓝图

## 一句话概括

> 用一句话讲清楚这个项目做了什么、解决了什么问题。

## 项目背景与定位

(由你根据 README 分析撰写)

- 这个项目诞生的背景是什么？解决了什么痛点？
- 之前的方案有什么不足？这个项目怎么改变的？
- 项目在生态中的位置（官方/社区/企业维护？被谁使用？）

## 突破性特点

(这个项目最让人眼前一亮的 2-3 个点，简明扼要)

- 对比之前的做法，这个项目有什么本质性的不同？
- 有没有开创性的理念或范式？

## 设计亮点

(深入分析具体设计，每个亮点说清楚「好在哪、为什么好」)

## 怎么用

- 典型使用场景
- 适合什么项目？不适合什么项目？
- 上手难度
- 已知坑点

## 架构详解

(技术架构分析，**必须包含线稿图**)

- 核心技术栈
- 分层架构 / 模块划分（线稿图）
- 核心数据流 / 请求处理流程（线稿图）
- 关键目录职责

## 概览

| 字段 | 值 |
|------|-----|
| URL | ... |
| Stars | ... |
| 语言分布 | ... |
| ...  | ... |

## 项目健康度

- 活跃度、发版节奏、社区规模
- 值得关注的 Issue/PR

## 附录

(脚本采集的原始数据，折叠展示)

<details>
<summary>目录结构</summary>
(脚本自动采集)
</details>

<details>
<summary>Releases / Issues / PRs / 贡献者 / 同类项目</summary>
(脚本自动采集)
</details>
```

## 分析指南

脚本只采集数据。以下维度需要你做智能分析：

### 1. 项目健康度

- **活跃度**：last push 在近 3 个月内 = 活跃
- **社区规模**：贡献者 > 10 = 有社区基础
- **维护质量**：open issue 数 vs closed issue 数的比例
- **发版节奏**：release 频率是否稳定

### 2. 技术架构

从目录结构和 README 推断，并**用线稿图可视化**：

- 单体 vs 微服务 vs monorepo
- 前后端分离？
- 有无测试目录（质量信号）
- CI/CD 配置（.github/workflows/）
- 文档质量

#### 线稿图规范

架构总结必须包含至少一张线稿图。线稿图用纯文本绘制，放在 markdown 代码块中，用于表达模块关系、分层结构或数据流。线稿图比纯文字更直观，能让读者一眼看懂项目结构。

**分层架构图**（适用于大多数项目）：

```
┌─────────────────────────────────────────┐
│                  CLI                     │
│            (bin/, cli/)                  │
├─────────────────────────────────────────┤
│          Application Layer              │
│        (server/, client/)               │
├──────────────┬──────────────────────────┤
│  Module A    │    Module B              │
│  (auth/)     │    (api/)                │
├──────────────┴──────────────────────────┤
│            Core / Shared                │
│          (lib/, utils/)                 │
├─────────────────────────────────────────┤
│          External Dependencies          │
│        (database, 3rd-party)            │
└─────────────────────────────────────────┘
```

**数据流图**（适用于管道/处理流程）：

```
Input ──▶ Parser ──▶ Transformer ──▶ Optimizer ──▶ Output
            │              │              │
            ▼              ▼              ▼
         AST Cache    Plugin System   Code Cache
```

**模块依赖图**（适用于多包/monorepo）：

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│  pkg-a   │────▶│  pkg-b   │────▶│  pkg-c   │
└──────────┘     └────┬─────┘     └──────────┘
                      │
                      ▼
                ┌──────────┐
                │  shared  │
                └──────────┘
```

**请求处理流图**（适用于 Web 框架/服务端项目）：

```
Request
  │
  ▼
Middleware Chain ──▶ Router ──▶ Handler ──▶ Response
  │                    │           │
  ▼                    ▼           ▼
Logger              Match       Business
Auth               Rules        Logic
CORS                            │
                                ▼
                            Database
```

根据项目特征选择合适的图类型，也可以组合使用。图不需要面面俱到，重点表达核心架构骨架。

### 3. 设计亮点分析

这是蓝图最核心的部分。不是泛泛地说「这个项目不错」，而是深挖具体的设计决策，说清楚**好在哪、为什么好**。

分析维度（不需要全覆盖，挑项目真正出彩的点）：

- **API 设计**：对外接口是否简洁直观？有没有巧妙的抽象让复杂操作变简单？（比如装饰器模式把注册流程压缩到一行）
- **模块划分**：代码组织是否清晰？职责边界是否明确？有没有优雅的分层？
- **核心机制**：项目最核心的技术实现是什么？用了什么模式/算法/策略？解决了什么难题？
- **性能策略**：有没有巧妙的性能优化手段？（缓存策略、懒加载、编译期优化等）
- **扩展性设计**：插件系统？Provider 模式？中间件机制？怎么让用户在不改源码的情况下扩展功能？
- **错误处理**：错误信息是否友好？有没有 graceful degradation？
- **开发者体验**：文档、CLI、脚手架、类型提示等方面有没有值得学习的做法？

写法示例：

```markdown
### 设计亮点

#### 1. 装饰器驱动的零配置注册

FastMCP 用 `@mcp.tool` 装饰器替代了传统的手动注册流程。
函数签名自动推导为 JSON Schema，Pydantic 类型自动变成参数校验。
这意味着开发者只需要写业务逻辑，框架处理所有协议层面的事。

#### 2. 双语言架构的桥接策略

Next.js 用 N-API 把 Rust 编译器（SWC/Turbopack）桥接到 Node.js 运行时。
性能关键路径（AST 解析、代码转换）在 Rust 侧完成，
运行时逻辑（路由、渲染、中间件）留在 JS 侧。
这个分界线划得很精准——Rust 只做 CPU 密集型任务，避免了跨语言调用的复杂度。
```

### 4. 适用场景

基于以上分析，总结：

- 适合什么场景使用？
- 不适合什么场景？
- 上手难度如何？
- 有什么已知坑？
