# 风格蓝图：从技术约束长出故事

本 Skill 参考「码农翻身」文章样本的高层叙事方法，并吸收克制、准确的中文技术写作原则。参考只用于研究方法，不表示可以复制原作表达。

参考项目：

- https://github.com/huangguangda/Code-farmers-turn-over
- https://github.com/Fenng/Tech-Doc-Style-Chinese

## 值得保留的高层特征

### 0. Why 先于 How

作者在前言和写作总结中反复强调：不要一上来讲安装、配置和使用步骤。先回答为什么会有这项技术、旧办法解决不了什么、它改变了什么，再进入怎么使用。

把写作当作一次「转教别人」：讲不顺通常不是文笔问题，而是理解中藏着未经验证的跳步。继续查资料、追问底层约束，直到能够用因果而不是术语串起文章。不要记流水账，也不要把孤立知识点并排堆放。

### 1. 技术对象成为叙事主体

让组件、协议或语言从自己的处境出发说话。主角并不知道自己在「给读者上课」，它只是在努力完成任务、保住资源、绕过限制或证明价值。

有效的人设来自真实属性：

| 技术属性 | 可转译的处境 |
|---|---|
| 很快但容量小 | 动作迅速，却只能同时记住少量事情 |
| 共享且会竞争 | 多个角色争用同一个入口、名额或账本 |
| 异步返回 | 交出任务后先做别的事，结果以后送回 |
| 有序要求 | 每个包裹都带编号，缺一件就不能交付 |
| 缓存命中 | 常用物品放在手边，没找到才去远处取 |

表格只用于设计，不应原样塞进正文。

### 2. 先展示痛苦，再命名办法

读者先看到旧方案为什么撑不住，才会在新机制出现时产生理解。常见推进是：

```text
原本可用 → 环境变化 → 旧办法失败 → 失败留下证据
         → 角色被迫改变 → 新机制暂时奏效 → 新边界出现
```

不要在开头先把定义、优点、缺点全部讲完。那会消耗故事的发现感。

### 3. 用对话暴露认知差

好对话让两方因为目标、视角或信息不同而冲突。若删掉引号后内容仍是一段完整百科解释，这通常是「对白皮肤的说明书」。

### 4. 章节像连续的实验

每章只改变一个关键条件，让读者观察后果。前一章的解决办法可以成为下一章的限制，但新问题必须改变选择或代价，不能只是增加下一个术语。

### 5. 及时揭底，而不是让读者猜到底

故事可以先降低抽象度，但最终要把真实术语、映射和边界说清。短寓言适合结尾集中揭底；设计复盘、历史演进和长篇架构故事可以在每次机制出现后就地命名。技术科普的目标是可迁移的理解，不是猜谜。

## 需要主动更新的部分

早期互联网文章常用密集感叹号、身份标签、输赢叙事和流行词制造节奏。新文章宜保留亲切、幽默和反差，但减少：

- 带贬义或过时的群体标签
- 把技术生态写成唯一赢家和彻底失败者
- 没有来源的夸张性能数字
- 用「震撼」「颠覆」「王者」替代实际变化
- 为了热闹让每句话都成为台词

## 原创边界

不要复用以下表达层内容：

- 原作标题公式和标志性角色名
- 已有朝代、人物关系、名场面和故事结局
- 可辨认的对白、段落节奏或连续情节
- 只替换技术名词的同构改写

可以复用的是抽象方法：Why-first、第一人称、限制驱动人设、失败驱动机制、短章节、对话冲突和术语揭示。每次从新的事实账本重新选场景，让故事因当前主题而生。
