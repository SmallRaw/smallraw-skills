# 技术拟人叙事写作

把技术机制写成一篇能读下去、能复述、经得住技术核对的原创中文故事。鲜明风格来自「角色的处境就是技术约束，情节的后果就是机制解释」，不是给名词换上古装或工牌。

## 先守住四条线

1. **事实线**：不编造版本、年份、性能数字、产品能力或因果关系。会变化的事实先查一手来源；资料不足时缩小断言或标出待确认。
2. **原创线**：用户要求模仿具体作者或作品时，只提炼高层特征并创作新的表达。不要复用参考作品的人名、标志性角色、标题结构、段落、对白或情节；尤其不要直接使用「CPU 阿甘」「大明邮差」等现成设定。
3. **解释线**：每个核心概念都要通过角色的一次行动、失败、代价或反馈显形。角色口头说出定义，不算解释完成。
4. **叙事线**：一篇文章只保留一条因果主线。短篇通常承载 1–3 个紧密机制；长篇可以更多，但每个机制都必须推进同一段演进。不要把产品清单逐个变成角色，也不要用连续参观替代故事。

## 判断任务模式

- **从零写作**：用户给主题或资料，直接完成事实整理、故事设计和成稿。
- **改写成故事**：保留原文事实、限制与确定程度，重做叙事入口、角色和冲突；不要为了戏剧性改变结论。
- **续写或扩写**：先提取现有稿的人称、世界规则、角色能力和未解决冲突，再延续；不要突然换一套隐喻。
- **审稿**：先按质量闸门指出问题和修复方向。用户未授权改写时，不直接替换原稿。

## 与相邻 Skill 的路由

- 本 Skill 负责**直接创作或重新设计故事**：从事实出发选择叙事引擎、人物和冲突，一次完成文章。
- `technical-story-explainer` 负责**重型生产流程**：复杂产品比较、高风险事实、独立研究、多 Reviewer 和返工闸门。
- `technical-story-explainer-polisher` 负责**保留原戏码的润色**：已有事实闭合的故事底稿，只改善表达、沉浸感和节奏。

已有说明文字若需要被重新设计成一个全新寓言，仍属于本 Skill；已有故事若人物、场景和解释映射都已锁定，只需变得更好读，则交给 polisher。

若用户只给主题，默认受众是有好奇心、略有技术背景但不了解该主题的读者，篇幅采用中等长文。不要承诺没有任何前置知识的读者也能看懂；先写清最低前置知识，并在正文补足必要桥梁。只有缺失信息会明显改变主题、事实或发布形式时才询问；其余细节自行做保守选择。

## 写作流程

### 1. 建立文章合同

在内部明确以下内容，不必默认展示：

- 读者最后要能用白话回答的中心问题，以及最低前置知识
- 短篇必须讲清的 1–3 个机制；长篇的因果主线和认知负荷上限
- 事实来源、时效和用户给出的不可改动内容
- 目标篇幅、发布载体和用户要求的人称或语气
- 真实术语是就地命名、结尾集中揭示，还是两者混合

### 2. 先搭一架 Why 梯子

写故事前连续回答：

1. 它出现以前，人们怎么解决这个问题？
2. 旧办法在什么条件下失败，留下什么可观察证据？
3. 新机制改变的是资源、时序、职责，还是信息？
4. 为什么不能用一个更简单的办法？
5. 它解决问题后留下什么成本和边界？
6. 哪一步还只能靠猜，需要继续查资料？

故事只覆盖已经答清的因果。若讲不顺，不要用修辞补洞；回到资料和底层机制继续追问。

### 3. 建立事实账本

把材料分为「必须准确出现」「可用情节转译」「证据不足不能写」三类。涉及当前产品、API、模型、价格、版本或生态现状时，先查官方文档或其他一手来源。完整方法见 [事实与隐喻边界](references/fact-and-metaphor.md)。

### 4. 选择一个主叙事引擎

优先从以下六种中选一个，必要时只用另一种做局部补充：

- **组件自述**：适合线程、缓存、数据库索引、令牌等有稳定职责和限制的对象。
- **成长或兴衰史**：适合语言、框架、协议和架构范式的演进。
- **制度寓言**：适合分层、路由、权限、共识和组织协作，但必须核对映射边界。
- **事故追查**：适合死锁、缓存击穿、丢包、数据竞争和性能退化。
- **设计推导**：适合从需求一步步推导接口、抽象、模式或架构，而不是先给标准答案。
- **威胁升级**：适合安全、信任链和容错；每个方案都由下一次攻击或反例检验。

读取 [叙事引擎与结构](references/narrative-engines.md)，为所选引擎完成最小故事卡。

### 5. 让人设从机制里长出来

为主角写清：想完成什么、天生擅长什么、做不到什么、依赖谁、最怕什么。性格必须来自这些约束。例如「动作极快但记不住太多东西」可以来自处理器与寄存器限制；不能先决定写一个暴躁老板，再硬找技术名词对应。

控制角色数量。每个有名字的角色都要推动因果、制造限制或带来反馈；只负责念定义的角色应删除或合并。

### 6. 用失败推动新机制出现

按「目标 → 旧办法 → 撞墙 → 证据/代价 → 新办法 → 新代价或边界」组织推进单元。短篇通常需要 2–5 个，长篇按因果主线展开。新概念要在读者已经看到它为何需要之后出现。

- 对话用于暴露误解、争执和权衡，不用于轮流背百科。
- 图示、代码和数字只在能缩短解释时出现。
- 一旦隐喻会误导，立即用一句作者旁注或结尾揭底校正，不要为了维持世界观牺牲准确性。

### 7. 写成稿，并选择揭底位置

短寓言可采用以下结构，其他引擎按自身因果组织，不强套三幕：

```markdown
# 有具体矛盾或悬念的标题

[用一次动作、麻烦或反常结果开场，不先下定义]

## [第一幕：目标和旧办法]
## [第二幕：限制暴露]
## [第三幕：新机制与代价]

## 技术揭底（独立章节可选）
- 故事中的关键事件分别对应什么真实机制
- 哪些地方是为了叙事做的简化
- 这个类比在哪些边界会失效
```

揭底有三种合法位置：每幕之后就地命名、故事结束后集中揭示、两者混合。短类比通常集中揭底；设计复盘、历史演进和长篇架构故事更适合就地命名。无论采用哪种，都要交代关键简化和类比边界。默认只交付文章成稿，不展示事实账本和故事卡；用户要求方案、审稿记录或资料来源时再附上。

### 8. 中文编辑与终审

终稿前读取 [中文叙事编辑规则](references/chinese-style.md) 和 [质量闸门](references/quality-gates.md)。按优先级修：事实与因果 → 隐喻边界 → 情节连续性 → 读者理解 → 语言和排版。

## 成稿标准

- 在首屏或全文前 10% 尽快出现具体目标、麻烦或反常现象。
- 删除技术名词后，主要情节仍然成立；恢复技术名词后，关键映射又能准确对上。
- 每个必须讲清的机制至少有一处可观察后果，读者能说出「为什么需要它」。
- 高潮之后尽快收束，不在故事已经结束后追加半篇说明书。
- 术语揭示短而直接，明确简化和失效边界，不重复全文。
- 语言口语化但不低幼，不依赖过时网络梗、标签化称呼或密集感叹号制造热闹。

## Gotchas

- **换皮说明书**：把线程叫「小线」、把内存叫「仓库」，然后继续逐条讲定义。修复：让角色先做事并承担错误后果。
- **角色与产品一一对应**：每个框架都化身为一位选手，文章变成产品走秀。修复：围绕同一问题写选择和代价，产品差异放到揭底。
- **隐喻反客为主**：为了圆故事新增技术上不存在的层级或能力。修复：修改故事世界，不修改事实。
- **靠对白讲课**：角色连续几段完整解释概念，却没有行动。修复：把定义变成任务、阻碍、回执或失败证据。
- **只有爽点没有边界**：新机制一登场就解决所有问题。修复：补上成本、适用条件或下一层限制。
- **照搬参考作品**：沿用熟悉的人名、朝代、名场面或句式。修复：退回机制约束，重新选择叙事引擎和场景。
