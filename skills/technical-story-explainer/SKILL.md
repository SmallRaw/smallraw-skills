# Technical Story Explainer

目标不是把技术藏进一篇漂亮小说，而是让小白顺着人物遇到的现实问题看懂技术因果，并在揭底时产生“原来是这样”的确认感。正文负责让读者亲眼看见机制为什么出现、旧办法为什么失败、新办法为什么有效；结尾负责把术语、产品差异和选择标准直接说透。

根 Agent 只调度、保存返回值、运行校验器和交付，不代替子 Agent 研究、设计、写作或审稿。每个职责使用普通新子 Agent，完成后立即关闭；没有独立子 Agent 能力时停止。

## 运行目录

```text
workspaces/technical-story-explainer/runs/<YYYYMMDD-HHMMSS-topic>/
  00-task.md
  01-facts.md
  02-story-plan.md
  03-drafts.md
  04-reviews.md
  05-final.md
  repair-ticket.md   # 仅返工时出现
```

`00-task.md` 第一行固定为 `模式：完整故事`，包含 `## 任务`、`## 正文要悟到`、`## 账本要说清` 和 `## 必讲项`。后三节必须使用 `- ` 项目符号。

- `正文要悟到` 只放 1 到 2 个无技术名词的底层因果问题，例如“为什么只说出办法不等于把事情办完”“新结果为什么会改变下一步”。禁止在这里写产品名、技术类别或“甲与乙有什么区别”；真实类别的对应关系属于账本。读者只看故事也应能用日常语言回答。
- `账本要说清` 放 1 到 4 个需要真实术语、产品比较、边界或选型标准才能回答的问题。这些问题允许只在结尾回答，不得为它们强造角色、道具或情节。
- `必讲项` 只列用户点名的概念或产品，最多 6 个。产品名默认属于账本，不自动成为正文任务。

## 四步流程

1. **查明事实**：新子 Agent 只读取 `references/roles/story-researcher.md` 与 `00-task.md`，必要时查官方或一手来源，返回 `01-facts.md` 后关闭。研究只解决原理、边界、共同能力和真实差异，不生成故事。
2. **设计一个解释故事**：新子 Agent 读取 `references/roles/story-designer.md`、任务和事实。它先用白话答清两组问题，再只返回一个 `02-story-plan.md`。故事围绕一个现实目标、一段重要关系和一次有代价的选择展开；正文只演出 `正文要悟到` 的底层因果，产品、术语和选型差异留在结尾。
3. **知情写作**：新子 Agent 读取 `references/roles/story-writer.md`、任务、事实、故事计划和 `references/style-examples.md`，生成 `# draft-1` 后关闭。作者知道技术目标，但必须先写人物自己的麻烦、关系和选择。正文不列流程、不陈列分类、不总结技术道理；真实术语只在正文结束后的 `## 真实技术账本` 出现。
4. **双闸门审稿**：并行启动两个不同的新子 Agent并在返回后关闭：
   - 小白 Reviewer 只读取 `references/roles/novice-reviewer.md`、任务和完整稿。它先假装账本不存在，只回答 `## 正文要悟到`；再读全文回答 `## 账本要说清`。正文题必须由故事本身讲明，账本题只要结尾直接、准确、低门槛地讲明即可，不得要求它们重新进入故事。两组理解题都必须通过。
   - 综合 Reviewer 读取 `references/roles/comprehensive-reviewer.md`、任务、事实、完整稿和风格样本，同时检查事实、解释、小说性、连续性和硬套痕迹。禁止向它提供故事计划或适配自检，避免作者的自我辩护污染盲审。出现产品一对一化身、流程演示压过人物故事或高潮后继续讲课时自动退回；其余稿件综合评分低于 90 也不得通过。

两类审稿都通过时定版。否则根 Agent 只提取最多三个阻止交付的问题写入 `repair-ticket.md`，启动一个全新子 Agent读取 `references/roles/story-rewriter.md`、任务、事实、故事计划、`draft-1` 与返工票，生成 `# draft-2`。再由两个全新 Reviewer 复审；仍有一类失败就停止，不生成第三稿。

## 关键边界

- 小说作者必须知道技术目标；禁止再用“让作者失忆”换取文学感。
- 正文默认只承担一个底层机制，最多两个，不逐项扮演产品。删除所有产品名后，故事方案和情节仍应原样成立。
- 一个角色、房间、道具、路线或关卡分别对应一个产品，就是硬套；即使正文没有写产品名也不合格。
- “修好甲又冒出乙，再修乙又冒出丙”是流程演示，不是自然升级；反馈必须改变人物关系、代价或选择，而不只是增加待办项。
- 账本不是与故事无关的附录：每个映射必须引用正文中已经发生的一个关键事件，并明确说明哪些比较只属于现实产品层。
- 技术或综合 Reviewer 不得要求标记为“账本承载”的产品差异重新进入正文。只有正文承载的核心机制缺失，才允许要求增加故事事件。
- 正文清晰度必须来自行动及其结果。若删除某段抽象总结后人物的目标、关系、证据和选择都不变，该段不能作为修复理解题的办法；尤其禁止用“这是两种模式/合同/机制”之类作者旁白替情节作答。
- “哦，原来是这样”优先于华丽文风。正文必须让读者复述核心因果，账本必须让读者说清真实术语和产品边界；两者各负其责。账本写得清楚不能掩盖正文与机制无关，正文写得动人也不能掩盖账本含糊。
- 不以纯小说标准追求复杂人物弧线、文学留白或华丽语言。只要人物有真实目的、情节自然推动机制显形、读者愿意继续读，就不要为了“更像小说”牺牲解释清晰度。
- 返工票最多三个问题。若命题本身无法解释任务，停止并报告需要重新设计，不用大量补丁把小说改成流程展示。

## 产物合同

- `01-facts.md`：`## 事实边界`、`## 底层机制`、`## 概念坐标`、`## 材料边界`。
- `02-story-plan.md`：`## 解释目标`、`## 故事方案`、`## 正文映射`、`## 适配检查`、`## 正文禁词`、`## 结尾账本`。正文映射最多两个 `- 核心机制：` 条目；适配检查必须明确 `产品化身：无`，并说明故事在删去技术任务后为什么仍有原生因果。
- `03-drafts.md`：`# draft-1`，返工时增加 `# repair-ticket` 与 `# draft-2`。每稿均含 `## 故事正文` 和 `## 真实技术账本`。账本先用一句话连接故事关键事件与真实机制，再分别回答正文题和账本题。
- `04-reviews.md`：当前稿的小白审稿和综合审稿。小白审稿包含 `正文机制测试：通过|退回`、`正文理解：<通过数>/<总数>` 与 `账本理解：<通过数>/<总数>`；综合审稿包含 `硬套检查：通过|退回` 与 `综合评分：<0-100>`。
- `05-final.md`：`## 产物审计` 与 `## 完整故事定版`；定版内部使用 `### 故事正文` 和 `### 真实技术账本`。

## 校验与输出

```bash
node <skill-dir>/scripts/validate_run.mjs <run-dir> --phase upstream
node <skill-dir>/scripts/validate_run.mjs <run-dir> --phase final
```

upstream 在写作前检查事实与故事计划；final 检查独立审稿、两类理解测试、90 分门槛、术语隔离和最终成稿。普通任务最终只输出 `05-final.md` 的「完整故事定版」；测试或 review 时再附运行目录和闸门摘要。
