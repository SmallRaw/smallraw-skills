# 更新模块知识

参数：可选模块/文件路径，以及 `--base <提交或分支>`。一次核对本次任务的全部变更，不逐 commit 写流水账。

## 确定范围

优先使用用户指定的 base、本次任务开始时记录的提交，或已确认的 PR 目标分支与当前 HEAD 的 merge-base。分支名称和起点不靠猜测，也不要默认只看最后一个 commit。

在确认基线后，将其赋给 `fractal_base`。先按调用位置解析路径参数，再从 Git 仓库根目录枚举全部变更，最后映射相关模块；从子目录运行 `git ls-files` 会漏掉其他目录的未跟踪文件：

```bash
cd "$(git rev-parse --show-toplevel)"
git diff --name-status --find-renames "$fractal_base"
git diff "$fractal_base"
git ls-files --others --exclude-standard
```

这会覆盖基线之后已提交、暂存和未暂存的受跟踪变更；未跟踪文件要另行读取。路径参数只缩小相关模块的检查范围，不省略该模块关联的测试、配置和文档。

如果没有可靠基线，先检查当前未提交变更，并明确报告“已提交部分尚未覆盖”。需要覆盖已提交内容且无法确定起点时，再带着候选范围询问用户，不把空的 `git diff HEAD` 当成任务没有改动。

## 核对知识

1. 将变更映射到实际模块，读取相关 README / MODULE / 现有设计说明，以及必要的实现、测试和历史。配置、测试、文档都可能改变模块约束，不按扩展名一概排除。
2. 判断已有说明的范围、流程、约束、取舍和证据是否仍成立且仍有独立价值。内部实现变化也要核对；都满足就不改文档。
3. 对新发现且容易再次误改的行为，优先用回归测试验证；原因或取舍无法由测试表达时，补最短说明和依据。不要仅为了让测试通过就删除旧行为要求；要求本身改变时说明原因。
4. 修正已失效的当前结论、相关入口和证据链接。详细历史留在 Git / issue 中，不逐 commit 追加；新增/删除普通文件不要求更新完整文件清单，也不逐层传播无关修改。
5. 仅按变更运行相关验证，并核对修改过的文档。纯文档更改只查内容和链接，不强制整个项目构建。

不要编造历史原因。无法确认的关键结论标明待核实并说明缺少什么依据；已知内容仍可继续处理。保留项目原有 Agent 指令，不自动移动或清理 `AGENTS.md` / `CLAUDE.md`。

输出：本次实际检查范围（含基线和是否覆盖已提交变更）、文档修改及原因、验证结果和待核实内容。无需修改也是有效结果。
