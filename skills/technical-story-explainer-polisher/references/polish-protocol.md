# 润色协议

用于把清楚稿润色成沉浸式技术故事。目标不是改事实，也不是重选戏码，而是让事实和戏码以更好看的方式发生在读者眼前。

## 编辑审稿

先审稿，再润色。审稿必须引用原文片段或行号，不能只写"通过"。

重点抓：

- 破壁说教：`这就是 X`、`本质上`、`在技术世界里`、`这里说明了`。
- 产品说明书腔：`X 是...`、功能列表、厂商定义段。
- 冲突不足：没有可见失败、损失、退件、错票、没改动的原件。
- 角色无性格：只有组件功能，没有脾气、限制、口头禅、社会位置。
- 隐喻误导：为了复用物件，反而混淆权限、状态或相邻概念。
- 视角跳动：上一句还在故事，下一句作者出来讲课。
- 字典补正文：正文没跑通，最后靠术语映射补救。

## 润色手术

常见替换：

- 作者总结 -> 角色动作和证据。
- 术语定义 -> 具体办事场景。
- 产品列表 -> 同一个任务连续翻车；每个产品/入口/后楼都用回执证明"能做什么、卡在哪里"。
- 参数差异 -> 表格退件、章名不认、标红降级。
- 流式格式 -> 一截一截吐出的回执，拼接规则和结束信号不同。
- 工具调用 -> 写传票、外部执行者办事、结果回到顾问桌上。
- Agent -> 任务板、权限单、回执循环、失败重试、交付证据。

## 对齐 sanity-check（不重做戏码）

`02-role-world-alignment.md` 是 polisher 的最轻产物，**不是重做 explainer 的工作**。

explainer 在 `01-research-and-concepts.md` 的戏码地图里已经为每个概念选了 `prototypes.md` 的原型 + 给了角色具体化。polisher 拿到这套设计后，只做 sanity-check：

```text
## 对齐 sanity-check

### 上游戏码地图核对
- explainer 选用的原型清单（从 01 复制，不重选）：
- 角色清单（从 01 / 03 复制，不重写）：

### 多原型组合的舞台一致性
- 如果 explainer 选了 2-3 个主原型，它们在同一个舞台里能不能并存？
- 还是出现"一边用仓库门，一边用合同账本"这种拼贴？
- 拼贴时怎么解决：合并舞台 / 退回 explainer 重选戏码 / 在润色里增加过渡说明？

### 缺失或冲突
- 戏码地图里有没有缺角色 / 缺道具 / 缺回执的段落？
- 有任何冲突就退回 explainer 重写戏码地图，**不要 polisher 自己重新选戏码**。

### 世界转场检查（如果起点 ≠ 中段世界则必检）

如果主角起点是现实世界（在工位 / 用电脑 / 用应用），而中段进入隐喻世界（柜台 / 楼 / 调度员 / 施工队 / 大厅），必须设计：

- **入口仪式**：现实 → 隐喻的过渡（做梦 / 翻开图 / 想象 / 同事递地图 / 视野淡入）
- **出口仪式**：隐喻 → 现实的过渡（醒来 / 合上书 / 大厅淡掉 / 回到工位）
- **中段每个新元件出场时的物理铺垫**：必须有"主角走到 / 转身 / 看见"的动作，不能"突然出现一个 X / 旁边冒出 Y / 柜台后面有人"。

凭空召唤元件会被读者识别为"作者硬塞设定"，破坏沉浸。
```

这一节只产 sanity-check 结论，**绝对不要把 explainer 已经选的戏码再演一遍**——那是 stage-3 故事分镜师的工作。

如果发现戏码缺角色 / 缺道具 / 缺回执：**退回 explainer**，不要 polisher 自己补。理由：polisher 没有约束卡的事实边界，自己补容易越界事实。

## 封箱叙事

长文/视频稿默认前 80% 少用真实术语、英文缩写、字段名和产品定义句。每集不要插揭秘盒；主故事链跑完后，再用最后账本集中开箱。

允许保留少量真实词作为标题或任务要求，但正文必须尽量先用故事对象跑通机制。

## 产品进故事

产品名不要直接排列表，也不要写成主角参观地图。先让主角带着同一个任务连续碰壁：

```text
同一任务 -> 主角误判 A -> A 的回执证明能做什么/卡在哪里
上一张回执引出新误判 -> B 的回执证明能做什么/卡在哪里
上一张回执继续逼出问题 -> C 的回执证明能做什么/卡在哪里
最后开箱产品名和真实能力边界
```

如果润色计划写成"走到门 A 看定义、走到门 B 看定义、走到门 C 看定义"，必须退回重写。产品段需要的是连续事故链，不是导览路线。

真实能力必须遵守输入事实边界。不能为了戏剧性给产品增加未经确认的功能。

## 剧情压力链

在 `03-polish-plan.md` 里，后半段必须单独写一张压力链表。它不是状态树，只用来防止故事断气：

```text
段落/概念：
主角当前误判：
这次误判造成的具体失败：
失败证据：
谁被迫出场/哪层被迫分离：
这次解决了什么：
留下的下一场麻烦：
```

最低要求：

- 入口、服务器/API、兼容、bridge、产品名段都要有压力链。
- 失败证据必须是正文里能看见的东西：退件章、红单、没拼上的小票、权限拒绝、原件未变、复验失败。
- 不要只写"阿成明白了""阿成知道了"。理解不是事故，证据才是事故。
- 如果某段只剩定义、分类、检查清单，没有误判和失败证据，先重写计划，再写正文。

## 扩展度

清楚稿是骨架。沉浸化故事意味着读者跟着主角看见、听见、误判、抱怨、看回执，每个动作都占字数；如果润色稿字数和清楚稿基本相等，几乎一定是"换台词、不加戏"——这就是 polisher 在自己产物里最常见的失败模式。

定量目标（写入 `03-polish-plan.md` 末尾，最后由闸 7 复核）：

- 润色稿总字数 ≥ 清楚稿总字数 × 1.3。
- 每个主要概念段至少 2 段角色对话或内心独白。
- 入口、API、兼容、bridge、产品名段每段至少 1 次完整"主角误判 -> 回执反驳 -> 主角修正"链。

定性提醒：

- 字数膨胀来自加动作、加误判、加抱怨、加可见物件，不是堆形容词或灌水转场。
- 把"阿成明白了"换成阿成挨一次具体的退件章；把"这就是 X"换成同事/管理员/翻译员对阿成翻一个白眼，再递一张写着证据的回执。
- 哪段实在无法扩展，要在审稿里写"本段已最简，无法扩展原因：xxx"，不能默认通过。

## 状态纪律

润色不能改变：

- 原件位置。
- 谁有钥匙或权限。
- 谁实际执行工具。
- 状态是否改变。
- bridge 是否只能转换、不能创造能力。
- 兼容是否只是部分兼容。
- explainer 戏码地图里每个原型的"演时小心"列出的扭曲项（参见 `prototypes.md` 每条原型末尾）。

每个状态变化必须有证据：封蜡破了、页码被抽出、印章盖上、测试回执、diff、日志、分段小票、退件章。

## 口播节奏

视频稿可用短句、重复和钩子，但不要用空洞口号。每 20-40 秒最好有一个看得见的动作或证据物。

好转场：

- "阿言以为这下稳了。第二天，问题更大。"
- "这张绿单救了他一次，也埋下了下一场麻烦。"
- "门开了，但后楼不认这张表。"

坏转场：

- "接下来我们介绍..."
- "这说明了..."
- "第一种是...第二种是..."
