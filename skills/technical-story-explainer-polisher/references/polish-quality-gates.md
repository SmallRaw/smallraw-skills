# 润色质量闸

最终交付前使用。闸不过就回到 `02-role-world-alignment.md` 或 `04-polished-draft.md` 修改。

## 闸 1：事实不变

- 没有新增未经输入稿确认的产品/API/模型能力。
- 没有把“可能需要 bridge”写成“必须 bridge”。
- 没有把“部分兼容”写成“完全兼容”。
- 没有把建议写成执行、读取写成修改、送达写成成功。

## 闸 2：状态连续

- 原件、钥匙、权限、回执、工具执行者的位置和持有人清楚。
- 每个状态变化都有可见证据。
- bridge 只转换格式和标记边界，不创造对方不支持的能力。

## 闸 2.5：戏码地图对齐（不重做）

润色稿必须通过戏码不拔检查——核对每个概念在润色稿里的核心失败是否跟 explainer 戏码地图里选定的原型一致：

- 每个概念在润色稿里仍能识别出选定原型的"戏码 5 步"骨架（目标 → 旧办法 → 翻车 → 证据 → 补丁 → 复跑）。
- 每个概念在润色稿里没有触发选定原型"演时小心"列出的扭曲（参见 explainer 戏码地图或 `prototypes.md` 每条原型末尾）。
- 多个原型组合时，舞台是同一个主舞台，不是拼贴。
- 角色替换没有改变权限、状态和事实边界。
- Agent 类原型（如 P14 任务板）没有被写成一个无所不能的新角色。
- **世界连贯性**：每个新出场的元件（柜台 / 任务板 / 中间站 / 对照表 / 信物等）都能在润色稿里找到"主角怎么遇到它"的引文（走到 / 转身 / 看见）。起点世界 → 中段世界 → 终点世界之间有明确转场仪式（特别是起点是现实世界 + 中段是隐喻世界时）。

失败例：

- 原选 P13（岗位被设计死了），润色成"要求打开仓库门但没开"——原型整体走偏成物理隔阂类。
- 原选 P14（任务板看回执循环），润色成"调度员凭直觉规划全程"——触发 P14 的"演时小心"。
- 多原型组合时拼贴成"一边仓库门 + 一边合同账本"，舞台割裂。
- 为了统一世界，把产品能力写得比事实卡更强。
- **凭空召唤元件**：润色稿里突然出现"柜台后面有人 / 旁边一块木板挂上墙 / 中间站就出场了"，没有"主角走到 / 转身 / 看见"的物理铺垫。
- **跨世界跳切**：主角起点在工位用电脑，中段突然在"楼里走"，没有任何转场仪式。

闸 2.5 通过条件：

1. 每个原型在润色稿里都能找到引文，证明戏码 5 步还在 + 没踩演时小心。
2. 每个新出场元件都有物理铺垫引文。凭空召唤 ≥ 2 处直接退回。
3. 起点世界 ≠ 中段世界时，入口仪式和出口仪式都存在。

找不到引文 / 缺转场 / 凭空召唤 ≥ 2 处，结论必须写"退回"。

## 闸 3：故事代替讲义

失败条件：

- 正文频繁出现“这就是 X”“本质上”“这里说明了”。
- 产品段以“X 是...”连续排列表。
- 后半段变成主角参观地图、看门牌、听作者解释，而不是连续遇到误判和回执。
- 连续 5 行以上只有定义、分类、判断清单，没有新动作或证据物。
- 主要概念靠最后字典才理解。
- 一段塞入多个新概念，读者只能背词。

通过标准：

- 角色先遇到具体目标。
- 旧办法有小成功。
- 直觉越界后出现可见失败。
- 新补丁解决刚才的失败。
- 同类任务复跑成功。
- 后半段仍保留压力链：误判、失败证据、补丁/分层、下一场麻烦。

## 闸 4：产品段

真实产品登场时必须满足：

- 先作为门、工人、队伍、房间、名牌或工具清单进入故事。
- 至少有一次具体任务、权限差异或回执证据。
- 最后再映射真实名称。
- 能力边界用保守表达。

如果只是把 Codex CLI、Codex、Claude Code、Claude Desktop 逐个定义，失败。

如果只是让主角“走到某门前看牌子”，再由作者解释这个牌子是什么，也失败。产品段必须让同一任务产生不同回执，读者靠回执分清入口、Agent、服务器/API、兼容和 bridge。

### 自检证据（写“通过”前必须填）

闸 4 不接受裸写“通过”。最终审稿在产品段写结论前，必须在审稿里逐个产品列出：

```
- <产品名> -> <润色稿原文片段，含可见回执物件> -> <这条回执证明了什么 / 不能证明什么>
```

回执必须是同一任务下的可见结果：绿单、红单、退件章、缺章告示、拼不上的小票、卡住的工具面板、"这扇门退回"的字条、diff、git status、commit 候选、便条。不接受"主角看到门牌""门牌上写着"这种参观证据。

要求：

- 每个出现的产品都要给出回执片段。
- 至少 N-1 个产品提供"和上一张回执不同"的差异点，否则视为"逐个定义换皮"。
- 找不到回执的产品，结论必须写"退回"，并在审稿里列出缺回执的产品名，回 `02-role-world-alignment.md` 补"多回执地图"，再回 `04-polished-draft.md` 写出回执。

不要把"主角说看明白了""主角点点头"当回执——理解不是事故，证据才是事故。

## 闸 5：封箱与开箱

- 长文/视频稿正文主体不逐节插技术揭秘。
- 最后开箱只映射最关键术语，不变成全文索引。
- 读者不看开箱也能复述核心机制。

## 闸 6：读感

成稿应该比清楚稿更有：

- 人物目标。
- 性格缺陷。
- 对话和抱怨。
- 可见证据。
- 转场钩子。
- 紧张感或荒谬感。

但不能为了热闹引入和技术映射无关的装饰角色。

## 闸 7：扩展度

定量指标，过不去就回到 `03-polish-plan.md`。

- 润色稿总字数 ≥ 清楚稿总字数 × 1.3。等量替换式润色一律退回。
- 每个主要概念段至少 2 段角色对话或角色内心独白。
- 入口、API、兼容、bridge、产品段每段至少 1 次完整"主角误判 -> 回执反驳 -> 主角修正认知"链。

定量没达标时，不要靠堆形容词或灌水转场凑字数。回去给主角加动作、加误判、加抱怨、加可见物件，让事情真的发生在画面里。

如果某段真的无法扩展，要在审稿里写"本段已最简，无法扩展原因：xxx"，不能默认通过。
